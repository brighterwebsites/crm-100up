## 3. The one thing actually blocking an end-to-end quote

**The Calculator has no "Send system to CRM" button.**

The Link-quote modal tells the user, in so many words:

> In the calculator, press *Send system to CRM* (copies the quote JSON), then
> paste it here.

That button exists in `100UP_suite_V46.html` (the `100up-quote` payload is
built at line 2719). It was never ported to `CalculatorPage.tsx`. The receiving
half — parse, fuzzy-match to stock, set job value, apply — is fully built and
working in `modals.tsx`.

So the new app has a complete quote engine and a complete quote receiver, and
nothing joining them. **This is the MVP gate**, and it is also precisely what
Fred named as the next priority:

> then next we need to work on the calculators/estimators and how that
> transfers into customers/jobs

Helpfully, `createJob(name)` in `features/jobs/actions.ts` already creates the
customer and the job together, so the direct path is small.

## 5. Answered by Fred, 2026-09-20 — nothing outstanding

**Deye `AI-W5.1-10P1-AU-B` (single-phase 10 kW) is $1,900.** Confirmed. That
is the value already seeded by `20260811120001`, so no change was needed. The
10P3 (three-phase) remains $2,300, corrected separately in `20260811150001`.

Two things followed from it.

**1. `bugs.md` #9 was stale.** It still read "Open — add the product". The
product was added on 2026-08-11. Now marked Fixed.

**2. The Deye 10kW three-phase should never be quoted.** Fred's reasoning: a
three-phase inverter splits its rating across the phases, so a 10kW 3P gives
~3.33 kW per phase, which won't carry what an off-grid three-phase customer
expects to run. The Deye three-phase fallback is the **12kW** `AI-W5.1-12P3`;
his most recent build used Sigenergy only.

This turned out to be a divergence the rebuild was about to introduce rather
than a change to anything Fred uses. **V46 already agrees with him** — its
three-phase Deye path hardcodes 12kW in every mode (lines 2259 / 2283 / 2288 /
2295) and never selects the 10P3. But `system_config_inverters` is seeded by a
blanket join over every active inverter per brand (`20260811160001`), so the
new configurator had picked the 10P3 up as a three-phase tier that V46 would
never have offered.

Fixed in `20260920090001_deye_three_phase_12kw_only.sql`: the **tier** is
removed, the **`stocks` row stays** (real product, carries the CES catalogue
entry, needed for any historical job).

**There is no Deye 15kW.** The 15kW is Sigenergy's — `SigenStor EC 15.0 TP`,
the *small* of Sigenergy's three-phase range. Deye's AU three-phase range here
is 10P3 and 12P3 only.

### The trap this nearly set

Removing a tier isn't free. `quoteEngine.ts` filtered candidates hard on
`size_class === forceSizeClass` and returned `null` when nothing matched. With
the 10P3 gone, Deye three-phase has one tier against Sigenergy's three — so
forcing "small" or "medium" would have **silently blanked the Deye column**,
which is the exact failure the `size_class` design was written to prevent.

The engine now falls back to a config's remaining tiers for the phase when the
forced class matches none of them. That is V46's behaviour by construction:
the 12kW Deye answers every three-phase mode. Without this, porting 3 Phase
later would have hit an empty column with no obvious cause.

**On "just don't display Deye in 3-phase":** not taken. Fred named the 12kW as
the fallback and V46 offers it, so dropping Deye from three-phase entirely
would diverge from both. Removing one tier keeps the two brands comparable,
which is the point of the side-by-side screen.

**If Fred later wants a Deye 15kW, or any other tier:** one `stocks` row plus
one `system_config_inverters` row. Data entry, no code. That is what the
configurator design bought.

## 6. Sequencing and deploy

Deploy is push-to-`main`; Cloudflare Workers Builds rebuilds automatically.
Database changes go via `supabase db push` — never through an MCP connection
(convention 1; that has already broken the migration history once).

```
Sprint 1  ──► push ──► Fred can quote end-to-end in the new app
Sprint 2  ──► push ──► job/installer model matches what Fred asked for
Sprint 3  ──► push ──► safe for real installers and real data
                 └──► CUTOVER
```

Schema changes can still ship in one go — Fred is not yet depending on the app,
so no staged "deploy frontend, drop column later" dance is needed. **That flips
at cutover**, and Sprint 3 is the last sprint where it holds.

Regenerate `app/src/types/database.types.ts` after every migration.

## 7. Risks worth naming

1. **Bug #14 is the one that would actually hurt.** Fred's margin is readable
   by any authenticated installer. It isn't urgent while no installer has an
   account, and it becomes urgent the hour one does. Don't let Sprint 3 slip
   past the first installer invite.
2. **`import_from_export.py` is untested against the current schema.** The
   estimate above assumes rework, not a rewrite. Worth an hour of reading
   before committing to the Sprint 3 timeline.
3. **The pricing↔stock link is still a regex** (`normalizePart.ts`), and it
   fails silently. Bug #9 is one instance; the configurator rearchitecture is
   the real fix and it is explicitly deferred. Expect more silent BOM
   drop-outs, and make them loud: the Link-quote modal already shows a "no
   stock match" pill, so the Calculator's own BOM view should too.
4. **Free-tier auto-pause.** Seven days without DB activity takes the whole
   stack down. Five days had already elapsed when this plan was written.
