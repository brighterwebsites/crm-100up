### 3.4 — the import script was worse than "out of date"

Two separate problems, and the second is the one that mattered.

**The schema had moved.** `jobs` lost `name` / `email` / `phone` /
`contact_method` to `customers`, lost `fixes_needed` and `job_order`, and had
its three install dates renamed. `stock_ces_specs` was merged into `stocks`.
`receipts` became `purchase_orders`. `stocks.supplier_id` became
`preferred_supplier_id`. Every one of those made the old INSERTs fail.

**The catalogue is now curated, and the old script would have overwritten
it.** `stocks` carries planning costs Fred confirmed, the `usable_kwh` the
engine sizes on, CES specs, product types, phases, manufacturer links and
inverter size classes — none of which exist in the legacy export, and
`system_configs` references those stock ids. The old script inserted stock
rows straight from the export.

So the rewrite **never creates or reprices a stock row**. It matches the
export's ids against the live catalogue, aborts if any are missing, and
writes exactly one column: `qty`. Name drift is reported as a notice, because
a product can legitimately be renamed and the id is what binds the
allocation.

**A near-miss worth recording.** The clear-down was first written as
`TRUNCATE … CASCADE`. `stocks.preferred_supplier_id` references `suppliers`,
and CASCADE follows foreign keys — so truncating suppliers would have
truncated `stocks`, destroying the entire catalogue as collateral. Exactly
the thing the rewrite exists to prevent. It is now ordered `DELETE`s,
children before parents, which raises a foreign-key error instead of
cascading.

`--truncate` is opt-in for the same reason.

2295) and never selects the 10P3. But `system_config_inverters` is seeded by a

never have offered.

Fixed in `20260920090001_deye_three_phase_12kw_only.sql`: the **tier** is
removed, the **`stocks` row stays** (real product, carries the CES catalogue
entry, needed for any historical job).

**There is no Deye 15kW.** The 15kW is Sigenergy's — `SigenStor EC 15.0 TP`,
the *small* of Sigenergy's three-phase range. Deye's AU three-phase range here
is 10P3 and 12P3 only.

### The trap this nearly set

Removing a tier isn't free. `quoteEngine.ts` filtered candidates hard on
`size_class === forceSizeClass` and returned `null` when nothing matched. With
the 10P3 gone, Deye three-phase has one tier against Sigenergy's three — so
forcing "small" or "medium" would have **silently blanked the Deye column**,
which is the exact failure the `size_class` design was written to prevent.

The engine now falls back to a config's remaining tiers for the phase when the
forced class matches none of them. That is V46's behaviour by construction:
the 12kW Deye answers every three-phase mode. Without this, porting 3 Phase
later would have hit an empty column with no obvious cause.

**On "just don't display Deye in 3-phase":** not taken. Fred named the 12kW as
the fallback and V46 offers it, so dropping Deye from three-phase entirely
would diverge from both. Removing one tier keeps the two brands comparable,
which is the point of the side-by-side screen.

**If Fred later wants a Deye 15kW, or any other tier:** one `stocks` row plus
one `system_config_inverters` row. Data entry, no code. That is what the
configurator design bought.

### Rehearse it first — this week, not on the night

**The import is a complete replacement, not an increment.** `--truncate`
clears the operational tables and reloads everything, so every run produces
the same end state. Run it ten times and you get the same database.

That makes a full rehearsal free, and nothing in the CRM is real, so a failed
one costs nothing either. **Do it before the night**, when a surprise is a
Tuesday afternoon problem rather than an 11pm one.

```bash
# 1. Report only. Read it properly.
python scripts/import_from_export.py --export <fresh>.json --dry-run

# 2. Generate the SQL.
python scripts/import_from_export.py --export <fresh>.json     --emit-sql import.sql --truncate
```

Then paste `import.sql` into the **Supabase SQL editor**, which runs as
`postgres`. That matters: `private.guard_stock_qty()` and RLS both key off
`current_user`, so as an app user the stock quantities fail silently while
everything else succeeds. There is no local `psql` on this machine, so the
SQL editor is the route.

**What the rehearsal is actually testing** — the dry run against the
2026-06-25 export came back clean, so the *shape* is known good. A fresh
export may not be:

- a supplier whose name no longer matches anything (reported as a problem)
- a stock id in the export that is not in the live catalogue (the SQL
  **aborts** — deliberately, because the catalogue cannot be rebuilt from the
  export)
- a job at a stage/step that no longer exists (aborts)
- stock renamed since (a notice, not an error — the id is what binds)
- duplicate customers where one household has several jobs (expected, by
  design; merge by hand afterwards if Fred wants)

Each of those is a five-minute fix found early and an ugly surprise found
late.

**Rehearse the whole thing, not just the import:** apply it, then open the app
and check a few jobs against V46 — dates, stock allocations, stage. That is
the step that catches a mapping error the SQL was perfectly happy with.

Database changes go via `supabase db push` — never through an MCP connection
(convention 1; that has already broken the migration history once).

```
Sprint 1  ──► push ──► Fred can quote end-to-end in the new app
Sprint 2  ──► push ──► job/installer model matches what Fred asked for
Sprint 3  ──► push ──► safe for real installers and real data
                 └──► CUTOVER
```

Schema changes can still ship in one go — Fred is not yet depending on the app,
so no staged "deploy frontend, drop column later" dance is needed. **That flips
at cutover**, and Sprint 3 is the last sprint where it holds.
